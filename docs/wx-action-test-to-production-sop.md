# KTV Game Hub 小游戏接入与上线 SOP

更新时间：2026-07-23

依据：`KTV Game Hub 游戏上线 SOP.pdf` 第 3 步至第 8 步，以及历史项目执行过的“测试通过后提交 `master` 正式 MR”流程。

## SOP 的输入和目标

每次只处理当前项目下一个明确的小游戏：

```text
D:\AIproject\production\ktv-h5-extension\app-projects\<小游戏目录>
```

例如任务指定“包厢背锅王”，就读取：

```text
D:\AIproject\production\ktv-h5-extension\app-projects\room-blame-king
```

这个具体小游戏的源码、PRD、素材和验证结果是本次接入工作的输入。

公司接收仓库是：

```text
https://g.ktvsky.com/web/wx_action.git
```

目标是把该小游戏接入公司手机点歌 Game Hub，依次完成测试和正式上线。

```text
选定一个 app-projects 小游戏
  -> 按 wx_action 结构完成接入
  -> 提交 release/online 测试 MR
  -> 测试与验收通过
  -> 提交 master 正式 MR
  -> 前端人员打包正式上线
```

## 开始前确认

1. 用户已经明确本次要接入哪一个小游戏。
2. 只读取该小游戏目录和必要的项目级说明，不扫描或提交其他小游戏。
3. 确认小游戏是：
   - 直接转成 `wx_action` 内的 Vue 2 页面；或
   - 已有独立线上服务，只需要在 `wx_action` 增加入口和承载页。
4. 确认本次是否需要 PayModal、点歌和埋点。
5. 不假设某个固定的本地 `wx_action` 目录，不自行 clone 公司仓库；按当前任务提供的公司代码环境执行提交。

## 第 3 步：代码开发与接入

负责人：工程师。

1. 读取指定小游戏目录中的源码、PRD、素材和验证结果。
2. 基于公司仓库最新 `release/online` 准备该小游戏的 feature 分支。
3. 将指定小游戏接入 `wx_action`：
   - 转成 Vue 2 SFC，或增加独立游戏的承载页。
   - 注册不冲突的游戏路由。
   - 在 KTV Game Hub 增加大厅入口。
   - 接入该小游戏的正式封面和必要资源。
4. 按本次需求接入 PayModal、点歌和埋点。
5. 执行公司仓库实际提供的构建命令。
6. 检查本次变更只包含该小游戏，不包含其他 `app-projects` 产品或无关公司代码。
7. 不提交构建生成的 `dist/`。
8. 使用当前操作者的公司 Git 身份提交并推送 feature 分支。

PDF 中需要遵守的开发约定：

- Vue 2，Options API。
- 样式使用 `rem`、`vw`、`vh`。
- 需要支付时引用 `src/components/common/PayModal.vue`，不复制、不改写。
- 需要支付时在 `mounted` 中调用 `fetchPayPkg`。
- 定时器在 `beforeDestroy` 中清理。

产出：指定小游戏已经接入 feature 分支。

## 第 4 步：创建测试 MR

负责人：肖恩。

1. 创建 `小游戏 feature 分支 -> release/online` MR。
2. MR 不包含 `dist/`。
3. MR 描述写明：
   - 本次接入的小游戏名称。
   - 游戏入口、路由、页面和资源变更。
   - 是否包含 PayModal、点歌和埋点。
   - 本地构建结果。
   - 已完成的游戏流程验证。
   - 参考资料或独立游戏地址。

产出：测试 MR 链接。

## 第 5 步：Code Review

负责人：肖恩。

按照 PDF 检查：

1. feature 分支基于 `release/online`。
2. 公司仓库构建通过。
3. 没有修改与该小游戏无关的文件。
4. 路由路径不与现有游戏冲突。
5. 需要支付时，PayModal 引用路径正确。
6. 需要支付时，`fetchPayPkg` 在 `mounted` 调用。
7. 定时器在 `beforeDestroy` 清理。
8. 没有由本次变更新增的阻塞性控制台错误。
9. 没有硬编码密钥、Token 或其他敏感信息。

还要确认：

- 大厅封面和小游戏名称正确。
- 点击大厅入口可以进入指定小游戏。
- 手机尺寸下没有溢出、遮挡或无法点击。
- 多人游戏完成真实的加入、开局、同步和结算验证。

产出：Review 通过，或给出修改意见。

## 第 6 步：合并并部署测试环境

负责人：肖恩。

1. Review 通过后合并测试 MR。
2. 合并到 `release/online` 后触发测试环境构建和部署。
3. 检查流水线是否成功。
4. 打开测试环境检查大厅入口、页面、资源和控制台。

测试地址：

```text
https://kg.stage.ktvsky.com/action/ktv_game_hub
```

产出：指定小游戏进入测试环境。

## 第 7 步：真机验证

负责人：前端负责人。

1. 在目标手机 WebView 或微信环境打开测试地址。
2. 走完大厅入口、游戏开始、游戏过程和结果页。
3. 需要支付和点歌时，验证非 VIP、支付成功和点歌成功。
4. 使用 vConsole 或远程调试检查错误。
5. 多人游戏使用多台设备验证房间加入和状态同步。
6. 有问题时回到该小游戏 feature 分支修复，再走 MR；不直接修改公共分支。

产出：真机验证通过。

## 第 8 步：产品验收

负责人：产品负责人。

1. 在测试环境体验指定小游戏的完整流程。
2. 确认玩法、文案和视觉符合需求。
3. 明确确认“测试环境没问题，可以提正式”。

产出：正式 MR 许可。

## 第 9 步：提交 master 正式 MR

测试环境确认没问题后，参考历史上线流程，把该小游戏已验证的完整内容提交到正式 `master`。

负责人：肖恩提交 MR，负责人或前端人员合并。

1. 准备只包含该小游戏已验证内容的正式分支。
2. 创建 `小游戏上线分支 -> master` MR。
3. 确认正式 MR 包含测试通过时的完整内容：
   - 大厅入口
   - 路由
   - 游戏页面或承载页
   - 正式资源
   - 最终封面
4. 确认 MR 无冲突，不包含测试环境中的其他小游戏。
5. 在正式分支再次执行公司仓库构建。
6. MR 描述注明：
   - 测试环境已经验证通过
   - 本次小游戏名称
   - 源分支 -> `master`
   - 当前是否无冲突
   - 本次包含的完整变更
   - 构建结果
7. 由负责人或前端人员合并正式 MR。
8. 前端人员基于合并后的 `master` 打包并部署正式环境。

产出：正式 MR 链接，随后交给前端发布。

## 第 10 步：正式上线检查

前端人员通知正式部署完成后执行：

1. 打开正式 Game Hub。
2. 确认指定小游戏入口和最终封面已经出现。
3. 点击入口并走完一局。
4. 检查正式资源是否为本次版本。
5. 检查控制台和网络请求。
6. 多人游戏执行一次正式环境多人验证。

正式地址：

```text
https://kg.ktvsky.com/action/ktv_game_hub
```

产出：正式上线确认。

## 常见问题与处理

### 没有明确指定小游戏

先让用户指定 `app-projects` 下的目标小游戏，不能默认把整个项目提交到公司仓库。

### 误读了其他小游戏

停止操作，重新限定到用户指定的小游戏目录。提交前检查文件清单，确保没有其他产品内容。

### 不清楚如何接入公司仓库

先读取公司仓库现有同类游戏的路由、大厅入口和页面模式，沿用现有结构；不能凭空假设固定本地路径或自行 clone。

### 测试 MR 包含无关公司代码

检查 `git status`、`git diff --stat` 和 `git diff --name-status`，只保留该小游戏接入所需文件。

### 正式 MR 夹带其他测试小游戏

比较正式分支与 `master` 的完整差异。正式 MR 只能包含本次已验收的小游戏；不能把整个 `release/online` 合进 `master`。

### 测试版本和正式版本不一致

逐项核对入口、路由、页面、资源和最终封面。必要时比较文件 hash，确保正式 MR 使用测试通过的版本。

### 构建命令不一致

以公司仓库当时的 `package.json` 为准，不在通用 SOP 中写死命令。构建失败先判断是本次改动还是仓库既有问题。

### 构建产生 dist 变更

`dist/` 不进入 MR。清理本次构建产物后再检查源码差异。

### 提交身份错误

提交前检查 `git config user.name`、`git config user.email` 和最新提交作者。已经进入公共分支后不 force push。

### MR 已合并但正式站没有更新

确认前端人员是否已经基于最新 `master` 打包并部署。随后检查正式页面构建版本和静态资源，排除 CDN 缓存。

### 正式上线后需要回滚

对该小游戏的正式 MR 创建 Revert MR，Review 后合并，由前端重新打包。独立服务按其部署平台回滚，不删除数据库或数据卷。
